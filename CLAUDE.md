## Key decisions (don't re-litigate these)

- **Zero-cost-first POC**: browser mic + Web Speech API (STT) + `speechSynthesis` (TTS) is the primary build-and-test path all week. It's free and unlimited, so all iteration happens here.
- **Telephony provider: Twilio.** Chosen over Vapi/ElevenLabs because (a) it matches the swap-in path already documented in `ARCHITECTURE.md` §19 (Twilio Voice + Media Streams) with no rework, and (b) Vapi/ElevenLabs bundle orchestration around LLM-driven flow, which fights this project's deterministic server-side Auth State Machine (§17).
- **One Twilio number + browser-mic calling (not two Twilio numbers, not your phone).** Discovered Sep 23: Twilio trial accounts are hard-capped at one number ("Trial accounts are allowed only one Twilio number. To purchase additional numbers, please upgrade your account.") — a second purchase is blocked without upgrading to real billing, which we're avoiding. The one Twilio number is the "care line" (what the app answers on, `TWILIO_CARE_LINE_NUMBER`).
  - Original plan was to call it from the user's own cell, but the user is in India and the number is US — that's a real international/ISD charge from the Indian carrier (not from Twilio) to actually place that call, which conflicts with the zero-cost goal.
  - **Fix (decided Sep 23): call it from the browser instead**, using the Twilio Voice JS SDK — a small page (built as part of Saturday's work) that places a WebRTC call from the laptop's mic straight to the care-line number, no phone/carrier involved at all, drawing only from the same single Twilio account's trial credit. This is what Sunday's real test call will use.
  - Not wired to real webhooks until Saturday.
- **Testing policy — important**: do NOT place real Twilio calls iteratively during the week. Trial credit is limited and testing burns it fast. All logic gets verified via the browser Demo Mode and curl/Postman. Real phone calls happen **only on Sunday**, as a small deliberate batch of end-to-end verification calls — not a debugging loop. If a real call surfaces a bug, diagnose and fix it, re-verify via Demo Mode, and only place a fresh real call once you believe it's actually fixed.
- **AI engine: Google Gemini (free tier), not Claude.** Switched Sep 23 — Anthropic only offers a starter credit (documented as a cost exception in `ARCHITECTURE.md` §3), while Gemini has a genuine standing free tier, which fits the zero-cost-first approach better. The AI's job is unchanged regardless of provider: slot extraction, intent classification, and response phrasing only — it never makes the auth decision. The server-side Auth State Machine independently gates access to protected data (§17). `GEMINI_API_KEY` is in `.env`.
- **Gemini model: `gemini-3.1-flash-lite`, not `gemini-flash-latest`/`gemini-3.x-flash`.** Discovered Sep 24 while load-testing: the newest full "flash" models (whatever `gemini-flash-latest` resolves to, plus `gemini-3.6-flash`/`gemini-3.8-flash` directly) are hard-capped at **5 requests/minute** on the free tier — not enough for even one multi-turn demo call. The `-flash-lite` tier has a materially higher free quota and responds fast. Implemented via plain `fetch` against the Gemini REST API in `apps/server/src/lib/aiEngine.ts` (no SDK dependency — Node 24 has global `fetch`), with a 2-attempt retry on 429/503 (both observed under free-tier load) and a hard fallback to deterministic behavior (regex extraction / re-prompt / template phrasing) if the AI is unavailable — matches the existing "never fabricate an answer" guardrail, so an AI outage degrades gracefully rather than blocking the call.
- **Two separate, unrelated auth systems — requested Sep 25, built same day ("do it now").** (1) **Employee/company web login** — single company (Springfield Fiber), employees can sign up (every signup gets `ADMIN` — no invite/RBAC UI in scope) and log in to the ops dashboard. (2) **Customer self-service portal** — a *new* web login (email+password) for customers, completely separate from the phone-call BAN+PIN/OTP auth in `authStateMachine.ts`. Portal signup also sets the customer's phone PIN in the same step, so one new account works on both surfaces immediately (verified: signed up on the portal, then called in and authenticated with the same BAN+PIN). Deliberately NOT linked to the 9 seeded demo customers by email match, since several of those intentionally share one real inbox for OTP testing — portal signup always creates a fresh customer row (`nextCustomerId`/`nextBan` in `ids.ts`). Both sessions use httpOnly JWT cookies with **different cookie names** (`vn_employee_session` / `vn_customer_session`) and JWT `aud` claims, verified independently (`requireEmployeeAuth` / `requireCustomerAuth` in `apps/server/src/lib/auth.ts`) — no shared "user" table or role flag, so one session can never be mistaken for the other. Required switching CORS from wildcard to `{ origin: WEB_ORIGIN, credentials: true }` (cookies can't ride on `*`-origin CORS) and adding `cookie-parser`. DB: migration `002_customer_portal.sql` adds `customers.portal_password_hash` (nullable — demo-only customers have none); `migrate.ts` now tolerates re-running an `ALTER TABLE ADD COLUMN` (catches "duplicate column name" as a no-op) since there's no migration-tracking table. This also front-loads part of Saturday's plan (employee login + dashboard summary) — see the trimmed Sat entry below.

- **One website sign-in for everyone (changed Sep 23, user request — supersedes the separate employee/customer login *pages* above).** `/` redirects to `/login`; `/login` + `/signup` are plain website auth pages with no audience picker and no demo/OTP links. `POST /api/auth/login` (`routes/auth.ts`) checks employees first, then portal customers, and returns `redirectTo` (`/admin/dashboard` or `/portal/account`); `GET /api/auth/session` sends already-signed-in visitors home; `POST /api/auth/logout` clears both. The two *session types* stay separate exactly as before (own cookie/audience/table). Public signup always creates a **customer**; `POST /api/auth/employee/signup` now requires an employee session (Settings → "Add an admin") — an open admin signup on the public page would let anyone into the dashboard. Emails are unique across both tables (customer signup refuses employee emails). Demo call + OTP console moved to a "Demo tools" group in the admin sidebar. Old `/admin/login`, `/portal/login`, `/admin/signup`, `/portal/signup` redirect to the new pages. Also fixed: `JWT_SECRET` was read at import time, before `index.ts` loaded `.env`, so sessions were always signed with the insecure fallback — now read at call time (existing sessions were invalidated once).
- **Demo logins (Sep 23).** Admins: `priya.sharma@voicenexus.demo` / `admin-demo-pass`, `marcus.lee@voicenexus.demo` / `agent-demo-pass`. Normal users: all 9 seeded customers have a website password `<firstname>-demo-pass` (e.g. `amara-demo-pass`), and customers can sign in with **email or account number** (`BAN100001` or just `100001`) — needed because CUS004–006 share `ameydgaikwad@gmail.com` (Resend sandbox); for a shared email, login picks the account whose password matches. Set in `seed.ts` (`portalPassword()`); the live DB was updated in place rather than re-seeded, since the seed's `INSERT OR REPLACE` resets balances/payments.
- **Phone channel uses Twilio `<Gather input="speech dtmf">` + `<Say>`, not Media Streams + a separate STT vendor (decided Sat).** `ARCHITECTURE.md` §19 sketched Media Streams + Deepgram/Google STT, but that needs another account/API key; Gather is turn-based exactly like the demo's `/turn` loop, bills only against the same trial credit, and lets callers key BAN/PIN/OTP on the keypad. `routes/twilio.ts` drives the *unchanged* Auth State Machine via the shared `lib/conversations.ts` lifecycle. Twilio abandons webhooks after 15s and a turn can make several Gemini calls, so `/gather` answers within a 9s budget and otherwise `<Pause>`+`<Redirect>`s to `/pending` until the turn finishes. Recording is Twilio-native (`<Start><Recording>` → mp3 downloaded into `storage/recordings/`). All webhooks are signature-validated against `PUBLIC_BASE_URL` (the ngrok URL), not the Host header.
- **Resend sandbox only delivers to the Resend account owner (`ameydgaikwad@gmail.com`)** — `onboarding@resend.dev` returns 403 for any other recipient until a domain is verified. The 3 Email-OTP seed customers now use that address (the old `amey.gaikwad@nforcone.com` was also a typo).
